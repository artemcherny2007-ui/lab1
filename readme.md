# Система бронирования билетов на мероприятия

---

## 1. Описание проекта и предметной области

Приложение представляет собой консольную информационную систему для бронирования билетов на культурные и образовательные мероприятия. Система позволяет просматривать доступные события, оформлять билеты на пользователей, просматривать список активных бронирований, отменять бронь с автоматическим возвратом места в общий фонд, а также редактировать данные пользователей.

Проект разработан на языке **Python 3** с применением многослойной архитектуры (**Layered Architecture**), принципов **ООП**, **SOLID**, строгой типизации (**Type Annotations**) и стандарта кодирования **PEP 8**.

---

## 2. Архитектура проекта (18 классов)

Код разделён на 5 независимых модулей, каждый из которых отвечает строго за свою зону ответственности:

### Слой сущностей (`data_layer.py` — 4 класса)
Хранит модели предметной области с защищёнными атрибутами и доступом через свойства (`@property`):
* **`Event`** — модель мероприятия (`event_id`, `name`, `total_seats`, `available_seats`). Содержит методы управления состоянием мест: `reserve_seat()` и `release_seat()`.
* **`User`** — модель пользователя (`user_id`, `name`) с поддержкой валидируемого сеттера для смены имени.
* **`Ticket`** — модель билета (`ticket_id`, `event_id`, `user_id`), связывающая пользователя и мероприятие по их идентификаторам.
* **`TicketDetails`** — объект переноса данных (DTO), объединяющий номер билета, название мероприятия и имя владельца для безопасной передачи в слой интерфейса.

### Слой доступа к данным (`repository_layer.py` — 4 класса)
Отвечает за сериализацию, десериализацию и реализацию полного цикла операций **CRUD** (`Create`, `Read`, `Update`, `Delete`):
* **`BaseRepository(ABC)`** — абстрактный базовый класс, задающий единый контракт методов (`get_all`, `get_by_id`, `add`, `update`, `delete`).
* **`EventRepositoryXML`** — хранилище мероприятий в формате **XML** (`events.xml`) на базе стандартной библиотеки `xml.etree.ElementTree`.
* **`TicketRepositoryJSON`** — хранилище билетов в формате **JSON** (`tickets.json`) с механизмом автоинкремента первичного ключа.
* **`UserRepositoryJSON`** — хранилище пользователей в формате **JSON** (`users.json`) с поддержкой поиска по имени и создания новых записей.

### Слой бизнес-логики (`service_layer.py` — 2 класса)
Координирует работу репозиториев и проверяет соблюдение бизнес-правил:
* **`BookingService`** — основной сервис приложения. Принимает репозитории через конструктор (**Dependency Injection**), управляет бронированием, отменой билетов, переименованием пользователей и формированием детальных отчётов по билетам.
* **`InputValidator`** — класс проверки и нормализации пользовательского ввода (валидация положительных числовых ID и проверка имени на допустимые символы).

### Слой пользовательского интерфейса (`main.py` — 1 класс)
Отвечает за взаимодействие с пользователем через консоль:
* **`ConsoleApp`** — реализует интерактивное текстовое меню, считывает команды и перехватывает исключения бизнес-логики.

### Слой исключений (`exceptions.py` — 7 классов)
Иерархия пользовательских исключений, унаследованных от базового класса **`BookingError`**:
* **`StorageError`** — ошибки чтения/записи диска или повреждения структуры файлов XML/JSON.
* **`EventNotFoundError`** — запрашиваемое мероприятие не найдено.
* **`NoSeatsAvailableError`** — отсутствие свободных мест на мероприятие.
* **`UserNotFoundError`** — пользователь не найден в базе.
* **`TicketNotFoundError`** — билет с указанным номером не существует.
* **`ValidationError`** — некорректный ввод со стороны пользователя.

## 3. Реализация принципов ООП и SOLID

1. **Инкапсуляция:** все внутренние поля сущностей и репозиториев объявлены как защищённые (с префиксом `_`). Доступ к полям осуществляется через декораторы `@property`, а изменение количества свободных мест инкапсулировано внутри методов `reserve_seat()` и `release_seat()` класса `Event`.
2. **Наследование и Абстракция:** все репозитории наследуются от абстрактного базового класса `BaseRepository(ABC)` и реализуют его абстрактные методы; все кастомные ошибки наследуются от `BookingError(Exception)`.
3. **Полиморфизм:** единый интерфейс методов CRUD в репозиториях и перехват любых бизнес-ошибок единым блоком `except BookingError as e:` в слое представления.
4. **Принцип единственной ответственности (SRP):** сущности хранят состояние, репозитории отвечают только за файловый ввод-вывод, сервис — за бизнес-правила, валидатор — за проверку строк, а `ConsoleApp` — за вывод в консоль.
5. **Принцип инверсии зависимостей (DIP):** `BookingService` и `ConsoleApp` получают свои зависимости извне через конструктор (`__init__`), а слой интерфейса никогда не обращается к репозиториям напрямую.

## 4. Форматы хранения данных

* **`events.xml`** — хранит список мероприятий в виде XML-дерева с кодировкой `UTF-8`.
* **`users.json`** — хранит массив JSON-объектов зарегистрированных пользователей (`ensure_ascii=False`).
* **`tickets.json`** — хранит массив JSON-объектов активных билетов со связями `event_id` и `user_id`.

## 5. Инструкция по запуску

1. Убедитесь, что установлен **Python 3.10** или выше (внешние библиотеки не требуются, используются только стандартные модули `json`, `xml`, `abc`, `typing`).
2. Поместите файлы `exceptions.py`, `data_layer.py`, `repository_layer.py`, `service_layer.py` и `main.py` в одну директорию.
3. Запустите приложение командой:
   ```bash
   python main.py
